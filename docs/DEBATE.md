# Debate — Personal Site

> Lab 02 — บันทึกจาก Subagents / Teams


## Brand Strategist

> มุม brand เท่านั้น (ไม่รวม UX / Devil's Advocate) · สถานะ: เปิดถกเถียง ยังไม่ใช่ข้อสรุป

### 1. Positioning ชัดไหม

**ชัดในแง่ "นิสัย" แต่ยังไม่ชัดในแง่ "คุณค่าที่คนอ่านได้"**

- แก่นที่แข็งแรงที่สุดใน PROFILE คือประโยคใน Bio: *"ไม่ได้วิ่งไล่ตาม trend … อะไรน่าสนใจ อะไรใช้ได้จริง ก็ลองหยิบมาเรียนมาเล่นดู"* — นี่คือจุดต่าง (differentiator) ตัวจริง: **คนที่คัดของใช้ได้จริงมาลองแล้วเล่า** ไม่ใช่สายข่าว AI รายวัน
- จุดอ่อน: Interests 5 หมวด (AI agents, Cloud, ทำอาหาร, เที่ยว, การเงิน) ถ้าวางเรียงกันเฉย ๆ จะดูเหมือน "สนใจทุกอย่าง" → คนอ่านจำไม่ได้ว่าเว็บนี้คืออะไร สิ่งที่ร้อยทั้ง 5 หมวดเข้าด้วยกันได้คือ **วิธีคิด** (ลอง → ใช้ได้จริงไหม → เล่า) ไม่ใช่ตัวหัวข้อ
- ชื่อ **13หมาหมี / 13Mamee** มีบุคลิก น่ารัก จำง่าย เข้ากับโทน "สดใส สนุก" — เป็น asset ที่ควรใช้ให้เต็มที่ ไม่ต้องทำให้ดูเป็นทางการ

**สรุป positioning ที่เสนอ (ร่าง):** พื้นที่ของคนสาย IT ธรรมดาคนหนึ่ง ที่คัดเรื่องเทคและเรื่องชีวิตที่ "ใช้ได้จริง" มาลองเอง แล้วเล่าแบบเพื่อนเล่าให้เพื่อนฟัง

### 2. Headline vs Tagline

Headline ปัจจุบัน: **"คนธรรมดา ที่ชอบเรียนรู้"**

| | ข้อดี | ข้อจำกัด |
|---|---|---|
| ในฐานะ Headline | ถ่อมตัว เป็นกันเอง ตรงกับ Audience ที่เป็นเพื่อน/คนรู้จัก | กว้างมาก — ใครก็พูดประโยคนี้ได้ ไม่บอกว่ามาเว็บนี้แล้วจะได้อะไร และ agent ที่อ่านเว็บก็สรุปไม่ได้ว่าเว็บเกี่ยวกับอะไร |
| ในฐานะ Tagline | เหมาะมาก — เป็น "ตัวตน" สั้น ๆ ที่ติดใต้ชื่อได้ทุกหน้า | — |

**ความเห็น:** ประโยคนี้ทำงานได้ดีกว่าในบทบาท **tagline (ตัวตน)** มากกว่า **headline (คำสัญญากับคนอ่าน)** ควรแยกสองชั้น:

- **Tagline** (ติดกับชื่อ, คงที่): "คนธรรมดา ที่ชอบเรียนรู้" — เก็บไว้ตามเดิม
- **Headline** (บรรทัดใหญ่หน้าแรก, บอกว่าเว็บนี้มีอะไร): ต้องมีทั้ง *ทำอะไร* + *เรื่องอะไร* + *ด้วยน้ำเสียงแบบไหน*

ตัวอย่างร่าง headline (เสียงเจ้าของเว็บ):
- "ลองเอง ใช้ได้จริง แล้วค่อยเล่า — จาก AI agents ถึงเมนูในครัวค่ะ"
- "ฉันเรียนรู้ไปตามโลก แล้วเก็บเรื่องที่ใช้ได้จริงมาเล่าให้ฟังค่ะ"

> หมายเหตุ: ถ้าจะแยก tagline ออกจาก headline จริง อาจต้องมี heading ใหม่ใน PROFILE — เรื่องนี้เป็นการตัดสินใจเชิงโครงสร้าง (กระทบ parser) ให้ไปถกในรอบ DECISIONS ไม่ได้เสนอให้แก้ตอนนี้

### 3. Audience คือใคร ควรเน้นอะไร

PROFILE ระบุ 2 กลุ่ม:

1. **เพื่อนและคนรู้จักทั่วไป** — กลุ่มหลัก
   - ต้องการ: รู้ว่าช่วงนี้เจ้าของเว็บทำอะไรอยู่, อ่านสบาย, มีที่ทักทาย
   - ควรเน้น: ความอบอุ่น + ความสดใหม่ → ส่วน **"ตอนนี้กำลังสนใจ" (Now)** และ **Guestbook** คือหัวใจของ brand สำหรับกลุ่มนี้ มากกว่า portfolio
   - ระวัง: ศัพท์เทคหนัก ๆ (agent, Cloud) ควรมีประโยคแปลเป็นภาษาคนติดไว้ เพราะเพื่อนไม่ได้อยู่สาย IT ทุกคน
2. **AI / agent ที่เข้ามาอ่านเว็บ** — กลุ่มรองแต่เป็นจุดเด่นที่ไม่ค่อยมีใครคิด
   - ต้องการ: รู้ชัดว่าเจ้าของเป็นใคร สนใจอะไร โดยไม่ต้องเดา
   - ควรเน้น: headline ที่ "สรุปได้ในประโยคเดียว" — ยิ่งเป็นเหตุผลให้ headline ต้องเจาะจงกว่า "คนธรรมดาที่ชอบเรียนรู้"
   - เชิง brand: การเขียนให้ agent อ่านง่ายสอดคล้องกับความสนใจเรื่อง AI agents ของเจ้าของเองอยู่แล้ว → เป็น "หลักฐาน" ว่าเธอลองของจริง ไม่ใช่แค่พูด

**ลำดับความสำคัญที่เสนอ:** เพื่อน (อารมณ์ / ความเป็นกันเอง) > agent (ความชัดเจน / โครงสร้าง) — ทั้งสองกลุ่มได้ประโยชน์จาก *ข้อความที่ชัด* เหมือนกัน จึงไม่ขัดกัน

### 4. ข้อเสนอปรับโทน / ข้อความ 3 ข้อ

**ข้อเสนอ 1 — แยก Tagline (ตัวตน) ออกจาก Headline (คำสัญญา)**
- เก็บ "คนธรรมดา ที่ชอบเรียนรู้" ไว้เป็น tagline ใต้ชื่อ
- ให้ headline บอกคุณค่าชัด ๆ ว่ามาแล้วได้อะไร เช่น
  *"ลองเอง ใช้ได้จริง แล้วค่อยเล่า — ตั้งแต่ AI agents ไปจนถึงเมนูในครัวค่ะ"*

**ข้อเสนอ 2 — ใช้ "ลองแล้วเล่า" เป็นเส้นร้อย 5 หมวด แทนการเรียงหัวข้อเฉย ๆ**
- ทุกการ์ด Interest มีประโยคสั้นในรูปแบบเดียวกัน (ลองอะไร / ทำไม) เพื่อให้ 5 หมวดดูเป็นคนเดียวกัน ไม่กระจัดกระจาย เช่น
  - AI agents: *"ฉันลองให้ agent ช่วยทำงานจริง แล้วมาเล่าว่าตรงไหนเวิร์ก ตรงไหนยังไม่ใช่ค่ะ"*
  - ทำอาหาร: *"เมนูที่ฉันทำซ้ำบ่อยที่สุด เพราะง่ายและอร่อยจริงค่ะ"*
  - การเงิน: *"หลักคิดเรื่องเงินที่ฉันใช้อยู่ — ไม่มีตัวเลขส่วนตัวนะคะ"* (สอดคล้อง Privacy)
- สอดคล้องกับมุมเล่าเรื่อง About ข้อ 3 "ลองแล้วเล่า" ใน Brainstorm — แนะนำให้เป็นมุมหลัก โดยใช้ข้อ 1 "นักเรียนตลอดชีพ" เป็นฉากหลัง

**ข้อเสนอ 3 — ดันโทน "สดใส สนุก" ให้ถึงระดับข้อความ ไม่ใช่แค่สี**
- ตอนนี้ Bio สุภาพและเป็นกันเองแล้ว แต่ยัง "เรียบ" กว่าโทนที่ตั้งไว้ (สดใส สนุก) — ใช้ชื่อ 13หมาหมี เป็นตัวช่วยสร้างบุคลิก
- ใส่ microcopy ที่มีชีวิตในจุดสัมผัส (CTA, Guestbook, Contact, หน้าว่าง) แทนข้อความมาตรฐาน เช่น
  - Guestbook: *"แวะมาแล้วทักกันหน่อยนะคะ ฉันอ่านทุกข้อความเลยค่ะ"*
  - Contact: *"มีเรื่องอยากคุย อยากแนะนำอะไรให้ฉันลอง ส่งมาได้เลยค่ะ"*
  - ส่วน Now: *"ช่วงนี้ฉันกำลังหมกมุ่นกับ…"*
- ข้อควรระวัง: สนุกได้ แต่ไม่ใช้มุกที่ต้องรู้บริบทส่วนตัว (เพื่อนใหม่/agent อ่านไม่เข้าใจ) และไม่พาดพิงที่ทำงาน/สถานที่ตาม Privacy


## UX Critic

> มุมผู้เยี่ยมชม (end-user) เท่านั้น — ไม่ซ้ำประเด็น positioning / tagline ของ Brand Strategist · สถานะ: เปิดถกเถียง ยังไม่ใช่ข้อสรุป
> อ้างอิงสิ่งที่เว็บแสดงตอนนี้จาก `src/pages/*.astro` (อ่านอย่างเดียว)

### 1. PROFILE พร้อมสำหรับ 4 หน้าหรือยัง

| หน้า | ข้อมูลที่มี | ขาด / ปัญหา |
|---|---|---|
| Home | Name, Headline, Bio | หน้าแรกเอา **Bio ทั้งก้อน** มาแสดงซ้ำกับ About → ผู้เยี่ยมอ่านเรื่องเดิมสองรอบ · ยังไม่มีข้อมูล **Now** (Brainstorm ระบุเป็น Must แต่ไม่มี heading) |
| About | Bio 3 ย่อหน้า | พอใช้ได้สำหรับรอบแรก · แต่หน้าเขียนสัญญาไว้ว่า "timeline, skills และลิงก์จะอัปเดตเร็ว ๆ นี้" ซึ่ง PROFILE ไม่มีข้อมูลรองรับเลย |
| Interests | รายการ 5 คำ | **มีแค่ชื่อหมวด** ไม่มีคำอธิบาย / ตัวอย่าง / ไอคอน → หน้า Interests กลายเป็น bullet 5 บรรทัด ไม่มีเหตุผลให้คลิกเข้าไป · ไม่มี anchor/slug ให้การ์ดหน้าแรกลิงก์ลงหมวดตรง ๆ |
| Contact | `## Contact` (email placeholder, github/linkedin ว่าง) | **parser ไม่อ่าน `## Contact` เลย** → หน้า Contact ตอนนี้มีแค่ฟอร์ม ไม่มีช่องทางอื่น · ค่าว่าง (`github:`) ถ้าวันหนึ่งถูก render จะเป็นลิงก์เปล่า · `demo@example.com` เป็น placeholder ที่ผู้เยี่ยมอาจคิดว่าเป็นอีเมลจริงแล้วส่งไปหาย |

**สรุป:** Home/About พร้อมราว 70% · Interests และ Contact ยังไม่พร้อม — ขาด "เนื้อ" ต่อหมวด และขาดสัญญาข้อมูลของ Contact

### 2. จุดที่ผู้เยี่ยมจะสับสน

1. **"Audience:" โผล่บนหน้าแรก** — แสดงข้อความภายใน เช่น "AI / agent ที่เข้ามาอ่านเว็บ (เขียนหัวข้อให้ชัดเจน…)" ซึ่งเป็นโน้ตถึงคนทำเว็บ ไม่ใช่ข้อความถึงผู้อ่าน → เพื่อนที่เข้ามาจะงงว่าเขาถูกเรียกว่าอะไร · Audience ควรเป็นข้อมูลออกแบบ ไม่ใช่เนื้อหาสาธารณะ
2. **Eyebrow "Personal branding site"** เหนือชื่อ — ศัพท์ของคนทำเว็บ ไม่ใช่ของคนอ่าน
3. **ภาษาปนกัน** — เมนู/label/ปุ่มเป็นอังกฤษ (Name, Message, Send, Sign) แต่เนื้อหาเป็นไทยและ `lang="th"` → เลือกหลักเดียว (แนะนำ: เมนูสั้นอังกฤษได้ แต่ label/ปุ่ม/สถานะเป็นไทยตามเสียงเจ้าของ)
4. **ข้อความเทคนิคหลุดถึงผู้ใช้** — "ฟอร์มนี้โพสต์ไปที่ `POST /api/contact`", "อ่าน/เขียนผ่าน `/api/guestbook`", สถานะ `Error: ...` / `HTTP 500` ดิบ → เพื่อนที่ไม่ใช่สาย IT ไม่รู้ว่าต้องทำอะไรต่อ
5. **Contact vs Guestbook** — ทั้งคู่เป็นฟอร์ม "ชื่อ + ข้อความ" หน้าตาเหมือนกัน ผู้เยี่ยมไม่รู้ว่าอันไหน **ส่วนตัว** อันไหน **ทุกคนเห็น** → เสี่ยงคนพิมพ์เรื่องส่วนตัวลง Guestbook (แนะนำให้บอกชัดทั้งสองหน้า)
6. **ข้อความ "เร็ว ๆ นี้" ที่ขัดกับเนื้อหา** — หน้า Interests มีรายการอยู่แล้วแต่ยังเขียนว่า "อัปเดตรายการ…เร็ว ๆ นี้" ดูเหมือนเว็บยังไม่เสร็จ
7. **ไม่มีสิ่งที่ตอบว่า "แล้วช่วงนี้ทำอะไรอยู่"** — กลุ่มเพื่อน (audience หลัก) มาเพื่อสิ่งนี้ แต่ยังไม่มีส่วน Now
8. **หลังส่งฟอร์มไม่บอกความคาดหวัง** — ไม่บอกว่าจะตอบกลับไหม/ทางไหน/นานแค่ไหน และไม่บอกว่าอีเมลที่กรอกจะถูกเก็บ/แสดงหรือเปล่า

### 3. ข้อเสนอ IA

```
Nav:  หน้าแรก · เกี่ยวกับฉัน · สิ่งที่สนใจ · ติดต่อ  (+ Guestbook เป็นลิงก์รอง/ปุ่มในหน้าแรก)
Home      : ชื่อ + headline → Now 3–5 ข้อ → การ์ด Interests 5 ใบ (ลิงก์ลง /interests#slug) → CTA ทักใน Guestbook
About     : Bio เต็ม (ย้ายออกจาก Home, เหลือ 1 ประโยคบนหน้าแรก) → ลิงก์ "ดูสิ่งที่ฉันสนใจ"
Interests : 5 section มี heading ของตัวเอง + คำอธิบาย 1 บรรทัด + (ภายหลัง) รายการ TIL/สูตร/ทริป
Contact   : บอกก่อนว่าคุยเรื่องอะไรได้ → ฟอร์ม → ช่องทางอื่น (แสดงเฉพาะที่มีค่าจริง)
```

- หน้าแรกมีหน้าที่ "พาไปต่อ" ไม่ใช่ "เล่าทุกอย่าง" — Bio เต็มอยู่ที่ About ที่เดียว
- การ์ด Interests บนหน้าแรกกับหน้า Interests ใช้ **แหล่งข้อมูลเดียวกัน** (ไม่เขียนคำอธิบายสองที่)
- ผลพลอยได้กับ agent: หน้า Interests ที่มี `<h2>` ต่อหมวดอ่านง่ายกว่า bullet เปล่า

### 4. ข้อเสนอโครงสร้าง PROFILE (ต้องตัดสินใน DECISIONS — กระทบ parser)

> `src/lib/profile.ts` ตอนนี้อ่านแค่ `## Name / Headline / Bio / Audience / Interests` ทุกข้อด้านล่าง **ต้องมี D-id ใน `DECISIONS.md` ก่อน** แล้วจึงแก้ `profile.ts` + type `Profile` + เทสต์ (และตรวจ `/api/interests` ที่คืน `interests: string[]` ด้วย) — ห้ามเปลี่ยนชื่อ heading เดิม เพราะเว็บจะ fallback เงียบ ๆ

| # | ข้อเสนอ | ผลกระทบ |
|---|---|---|
| U1 | Interests เป็นรูปแบบ `- ชื่อหมวด — คำอธิบาย 1 บรรทัด` (คั่นด้วย ` — `) | ไม่เพิ่ม heading แต่ parser ต้อง split · ถ้าเปลี่ยน type เป็น object จะกระทบ `/api/interests` (สัญญา BE ↔ FE) |
| U2 | เพิ่ม `## Now` เป็น bullet 3–5 ข้อ | heading ใหม่ + field ใหม่ · ว่าง = ซ่อน section (อย่า fallback เป็นข้อความอังกฤษ) |
| U3 | ให้ parser อ่าน `## Contact` เป็นคู่ `key: value` และ **แสดงเฉพาะค่าที่ไม่ว่าง** | heading ใหม่ในมุม parser · ต้องตัดสินด้วยว่า placeholder `demo@example.com` จะแสดงหรือซ่อนจนกว่าจะมีของจริง (ข้อแนะนำ UX: ซ่อน แล้วให้ฟอร์มเป็นช่องทางหลัก) |
| U4 | Audience ไม่ render บนหน้าเว็บ | ไม่ต้องแก้ parser — เป็นการตัดสินฝั่ง FE |

### 5. Microcopy ตัวอย่าง (เสียงเจ้าของ: ฉัน/ค่ะ)

**Interests (คำอธิบาย 1 บรรทัด — ภาษาคน ไม่ศัพท์หนัก)**
- AI agents — ผู้ช่วย AI ที่ทำงานแทนได้เป็นขั้น ๆ ฉันลองใช้จริงแล้วมาเล่าค่ะ
- Cloud — เรื่องเก็บและรันระบบบนอินเทอร์เน็ต เล่าแบบคนเพิ่งหัดค่ะ
- การทำอาหาร — เมนูง่าย ๆ ที่ฉันทำซ้ำบ่อยค่ะ
- ท่องเที่ยว — ทริปที่ชอบ เล่าย้อนหลังนะคะ
- การเงินส่วนบุคคล — หลักคิดที่ฉันใช้ ไม่มีตัวเลขส่วนตัวค่ะ

**Contact**
- บทนำ: "อยากทัก อยากแนะนำอะไรให้ฉันลอง หรือมีคำถาม เขียนมาได้เลยค่ะ ข้อความนี้ถึงฉันคนเดียวนะคะ"
- Label: "ชื่อที่อยากให้ฉันเรียก" · "อีเมลสำหรับตอบกลับ (ไม่แสดงบนเว็บค่ะ)" · "ข้อความ"
- ปุ่ม: "ส่งข้อความ" · กำลังส่ง: "กำลังส่งค่ะ…"
- สำเร็จ: "ได้รับแล้วค่ะ ขอบคุณมากนะคะ ฉันจะตอบกลับทางอีเมลค่ะ"
- ผิดพลาด (แทน error ดิบ): "ส่งไม่สำเร็จค่ะ ลองตรวจช่องที่กรอกอีกครั้ง หรือลองใหม่อีกสักครู่นะคะ"

**Guestbook**
- บทนำ: "ข้อความตรงนี้ทุกคนที่แวะมาจะเห็นนะคะ ถ้าเป็นเรื่องส่วนตัว ส่งทางหน้าติดต่อได้เลยค่ะ"
- ว่าง: "ยังไม่มีใครทักเลยค่ะ มาเป็นคนแรกกันไหมคะ"

**Home / ส่วนอื่น**
- หัว Now: "ช่วงนี้ฉันกำลังสนใจ"
- CTA ท้ายหน้าแรก: "แวะมาแล้ว ทักกันหน่อยนะคะ"
- About (แทน "จะอัปเดตเร็ว ๆ นี้"): ตัดทิ้ง หรือ "อยากรู้ว่าช่วงนี้ฉันสนใจอะไร ไปดูต่อได้ที่หน้าสิ่งที่สนใจค่ะ"

### 6. ข้อสังเกตนอกขอบเขต UX (ส่งต่อ)

- Guestbook render ด้วย `innerHTML` จากข้อความผู้ใช้ → ขัดกับ Brainstorm "ไม่ render HTML ของผู้ใช้" — ฝากให้ owner ฝั่ง FE/QA ตรวจ (ไม่ได้แก้ในรอบนี้)


## Devil's Advocate

> มุมหาช่องโหว่ privacy · credibility · scope creep · สถานะ: เปิดถกเถียง ยังไม่ใช่ข้อสรุป
> อ้างอิงโค้ดปัจจุบันแบบอ่านอย่างเดียว (`src/lib/db.ts`, `src/pages/guestbook.astro`) — ไม่ได้แก้อะไร

### 1. ความเสี่ยง

**R1 — Contact form เป็น "หลุมดำ": เก็บลง SQLite แต่ไม่มีใครอ่าน**
- ความเสี่ยง: `insertContact` เขียนลง `contact_messages` อย่างเดียว ไม่มีแจ้งเตือน ไม่มีหน้า inbox ไม่มี export — เจ้าของจะรู้ว่ามีข้อความก็ต่อเมื่อเปิดไฟล์ DB เอง
- ทำไมสำคัญ: microcopy ที่ UX Critic เสนอ *"ได้รับแล้วค่ะ … ฉันจะตอบกลับทางอีเมลค่ะ"* จะกลายเป็น **overclaim ทันที** ถ้าเจ้าของไม่มีทางเห็นข้อความ เพื่อนที่ส่งมาแล้วเงียบหายจะเสียความเชื่อใจมากกว่าตอนไม่มีฟอร์มเลย
- ทางลด: ก่อน ship ต้องตอบให้ได้ว่า "ฉันจะอ่านข้อความยังไง ทุกกี่วัน" · ถ้ายังไม่มีคำตอบ ให้ใช้ข้อความที่ไม่สัญญาเกินจริง เช่น *"ได้รับข้อความแล้วค่ะ ฉันจะแวะอ่านเป็นระยะ ๆ นะคะ ถ้าเรื่องด่วนอาจตอบช้าหน่อยค่ะ"*

**R2 — เก็บ email คนอื่นไว้โดยไม่มีนโยบาย (privacy ของผู้เยี่ยม ไม่ใช่แค่ของเจ้าของ)**
- ความเสี่ยง: หัวข้อ Privacy ใน PROFILE ปกป้องแค่ข้อมูล **ของเจ้าของเว็บ** แต่เว็บกำลังเก็บ email + ชื่อ + ข้อความของ **คนอื่น** ไว้ถาวร ไม่มีกำหนดลบ ไม่มีคำอธิบายว่าเก็บไว้ทำไม · API contact ตอบ 201 พร้อม row (รวม email) กลับไปด้วย
- ทำไมสำคัญ: เว็บส่วนตัวก็ยังเข้าข่าย PDPA ได้ถ้าเก็บข้อมูลที่ระบุตัวบุคคลได้ · ไฟล์ `site.sqlite` อยู่บน volume ถ้า backup หรือ copy หลุด = email เพื่อนหลุดทั้งก้อน
- ทางลด: เขียนข้อความสั้นใต้ฟอร์ม *"อีเมลใช้ตอบกลับเท่านั้น ไม่แสดงบนเว็บ และฉันจะลบข้อความเก่าเป็นระยะค่ะ"* · กำหนด retention (เช่น 90 วัน) ใน DECISIONS · ให้ BE พิจารณาไม่ echo email กลับใน response · ยืนยันว่า `data/` อยู่ใน `.gitignore`

**R3 — Guestbook เปิดโล่ง: ไม่มี length limit ฝั่ง server, ไม่มี rate limit, ไม่มี moderation, ไม่มี pagination**
- ความเสี่ยง: `insertGuestbook` เช็คแค่ว่า "ไม่ว่าง" — Must list เขียนว่า "จำกัดความยาว" แต่ถ้าจำกัดแค่ `maxlength` ใน HTML ก็ bypass ได้ด้วย `curl` · `listGuestbook` คืน **ทุกแถว** ไม่มี limit · render ด้วย `innerHTML` (UX Critic ชี้ไว้แล้ว — ตรงนี้ขอยกระดับเป็น **blocker ด้าน security** ไม่ใช่แค่ "ฝากตรวจ" เพราะเป็น stored XSS บนโดเมนของเจ้าของ)
- ทำไมสำคัญ: บอตสแปมหาฟอร์มสาธารณะเจอเร็วมาก · ข้อความลามก โฆษณา หรือลิงก์ฟิชชิ่งบนหน้าที่มีชื่อเจ้าของ = brand เสียหายโดยตรง · ข้อความยาว 1 MB × หลายพันแถว = หน้า guestbook ล่ม · และไม่มีปุ่มลบ → เจ้าของแก้สถานการณ์ไม่ได้ นอกจากเข้า DB เอง
- ทางลด (ขั้นต่ำก่อน ship): (1) render เป็น text (`textContent`) (2) จำกัดความยาว name/message **ฝั่ง server** (3) ใส่ `LIMIT` จำนวนแถวที่คืน (4) honeypot field ง่าย ๆ (5) มีวิธีลบข้อความที่เจ้าของทำได้จริง — ถ้าทำข้อ (5) ไม่ได้ ให้พิจารณา pre-moderation หรือเลื่อน Guestbook ออกจาก Must (ดูข้อ 3)

**R4 — Guestbook ทำให้คนอื่นเปิดเผยข้อมูลของเจ้าของแทนเธอ**
- ความเสี่ยง: Audience หลักคือ **เพื่อนและคนรู้จัก** ซึ่งรู้ชื่อจริง ที่ทำงาน และจังหวัดของเจ้าของอยู่แล้ว อาจเขียนแบบ *"ดีใจด้วยนะ ○○ ที่ได้ย้ายไปบริษัท X"* ลง guestbook สาธารณะ
- ทำไมสำคัญ: กฎ Privacy ทั้งหมดใน PROFILE (ห้ามชื่อบริษัท/จังหวัด ฯลฯ) ถูกทำลายได้จากช่องที่เจ้าของไม่ได้เป็นคนเขียน · ยิ่งเว็บตั้งใจให้ **agent อ่านง่าย** ข้อมูลที่หลุดใน guestbook ก็ยิ่งถูกเก็บและสรุปต่อได้ง่าย — "optimize ให้เครื่องอ่าน" กับ "เปิดช่องให้คนอื่นเขียน" ขัดกันอยู่ในตัว
- ทางลด: บทนำ guestbook ต้องเตือนชัดกว่าที่ UX Critic เสนอ เช่น *"ข้อความตรงนี้ทุกคนเห็นนะคะ ช่วยอย่าพูดถึงชื่อจริง ที่ทำงาน หรือที่อยู่ของฉันนะคะ ขอบคุณค่ะ"* · ไม่ดึงเนื้อหา guestbook เข้า JSON-LD หรือ `llms.txt` และพิจารณาใส่ `noindex` ที่หน้า guestbook

**R5 — Overclaim ใน copy: "ลองแล้วเล่า" แต่ยังไม่มีอะไรให้เล่า**
- ความเสี่ยง: Brand Strategist เสนอ headline *"ลองเอง ใช้ได้จริง แล้วค่อยเล่า"* และการ์ดแบบ *"ฉันลองให้ agent ช่วยทำงานจริง แล้วมาเล่าว่า…"* — แต่ในรอบแรก TIL / มุมครัว / ทริป / Showcase อยู่ใน Nice หรือ Later ทั้งหมด → หน้าเว็บ **สัญญาว่าจะเล่า แต่ไม่มีเรื่องเล่าสักชิ้น**
- ทำไมสำคัญ: credibility ของเว็บส่วนตัวมาจาก "หลักฐาน" ไม่ใช่ "คำอธิบายตัวเอง" · หน้าที่บอกว่า "ฉันลองแล้วเล่า" แล้วคลิกไปเจอแค่ bullet แย่กว่าพูดถ่อมตัวตรง ๆ · เรื่อง "Cloud" ก็เหมือนกัน ถ้าเขียนให้ฟังเหมือนเชี่ยวชาญ คนสาย IT ที่อ่านจะถามต่อทันที
- ทางลด: ใช้ copy ที่เป็น **ความตั้งใจ** ไม่ใช่ **ผลงาน** จนกว่าจะมีเนื้อหาจริง เช่น *"ช่วงนี้ฉันกำลังหัดใช้ AI agents อยู่ค่ะ ลองแล้วได้อะไรจะค่อย ๆ มาเล่านะคะ"* · หรือดึงเนื้อหาจริง 1 ชิ้น (TIL 1 เรื่อง) ขึ้น Must เพื่อให้คำสัญญามีหลักฐาน

**R6 — "การเงินส่วนบุคคล" เสี่ยงทั้ง privacy และ credibility พร้อมกัน**
- ความเสี่ยง: แค่ประกาศว่าสนใจการเงินก็ชวนให้มีคำถามเรื่องลงทุน หุ้น หรือคริปโตเข้ามาทาง contact/guestbook · ถ้าวันหนึ่งเขียนบทความ อาจถูกอ่านเป็นคำแนะนำการลงทุน · และเมื่อเล่าจากประสบการณ์จริง กฎ "ไม่มีตัวเลขส่วนตัว" รักษาได้ยาก
- ทำไมสำคัญ: brand เสียหายจากเรื่องเงินหนักกว่าจากสูตรอาหารผิดมาก
- ทางลด: การ์ดหมวดนี้ต้องมี disclaimer ในตัว เช่น *"เล่าหลักคิดที่ฉันใช้เองนะคะ ไม่ใช่คำแนะนำการลงทุนค่ะ"* · ไม่จำเป็นต้องมีเนื้อหาจริงในรอบแรก

**R7 — Placeholder `demo@example.com` และช่องว่างใน Contact หลุดขึ้นเว็บ**
- ความเสี่ยง: Must เขียนว่า "แสดง email เป็น placeholder ไปก่อน" — การ **แสดง** placeholder บนเว็บจริงคือการโชว์อีเมลปลอมให้คนส่งไปแล้วหาย (UX Critic เสนอให้ซ่อน — ฉันเห็นด้วย และเสนอให้เป็นเงื่อนไขบังคับ ไม่ใช่แค่ข้อแนะนำ)
- ทำไมสำคัญ: เพื่อนที่ส่งอีเมลไปแล้วเด้งจะคิดว่าเว็บทิ้งร้าง · ถ้า JSON-LD `Person` ดึง email placeholder ไปใส่ agent จะจำอีเมลปลอมเป็นข้อเท็จจริง
- ทางลด: ตั้งกฎว่า "ค่าที่เป็น placeholder หรือว่าง = ไม่ render ทั้งใน HTML และ JSON-LD"

### 2. คำถามท้าทายที่ต้องตอบก่อน ship

1. ข้อความที่ส่งผ่าน Contact **ไปถึงเจ้าของได้ยังไง** — ถ้ายังตอบไม่ได้ ทำไมต้องมีฟอร์ม ไม่ใช่แค่บอกช่องทางติดต่อ?
2. ถ้าพรุ่งนี้มีสแปม 500 ข้อความใน guestbook หรือเพื่อนเขียนชื่อบริษัทของเจ้าของลงไป — **ใครลบ ลบยังไง ภายในกี่นาที**?
3. ข้อมูลของผู้เยี่ยม (email ใน contact, ชื่อใน guestbook) **เก็บนานแค่ไหน** ใครเข้าถึง `site.sqlite` ได้บ้าง และ backup ไปอยู่ที่ไหน?
4. ณ วัน ship ทุกประโยคบนหน้าเว็บที่ขึ้นต้นว่า "ฉันลอง…แล้ว" **มีหลักฐานให้คลิกดูไหม**?
5. JSON-LD `Person` จะใส่ field อะไรบ้าง — `name` ใช้แค่ "13หมาหมี" ใช่ไหม · `jobTitle` / `worksFor` / `address` ต้องไม่มี · ใครเป็นคนตรวจ?
6. "อ่านง่ายสำหรับ agent" หมายถึงยอมให้ crawler/AI เก็บทุกหน้ารวมถึง guestbook ด้วยหรือเปล่า — ถ้าไม่ ต้องตัดสินเรื่อง `robots` / `noindex` ก่อน ship
7. ส่วน Now "แก้ใน docs ได้ง่าย" — แต่ทุกการแก้ต้อง commit + deploy ใหม่ **ใครจะอัปเดต และถ้า 3 เดือนไม่มีใครอัปเดต** ส่วนนี้จะกลายเป็นหลักฐานว่าเว็บร้างหรือเปล่า?
8. Heading ใหม่ (`## Now`, `## Contact` ที่ parser อ่าน, Interests แบบมีคำอธิบาย) ทั้งหมดต้องผ่าน DECISIONS + แก้ `profile.ts` + เทสต์ — **รอบแรกจำเป็นจริง ๆ กี่อัน**?

### 3. สิ่งที่ควรตัดออกจาก Must

Must ตอนนี้มี 6 ข้อ แต่ **3 ข้อต้องแก้ parser หรือเพิ่มสัญญาข้อมูลใหม่** (Now, คำอธิบาย + ไอคอน Interests, Contact) และอีก 1 ข้อเป็นพื้นที่รับเนื้อหาจากคนแปลกหน้า — ไม่ใช่ "รอบแรกเล็ก ๆ" อย่างที่หัวข้อ "Scope บวม" ตั้งใจไว้

| รายการใน Must | ข้อเสนอ | เหตุผล |
|---|---|---|
| ส่วน **Now** (3–5 bullet) | **ย้ายไป Should** | ต้องมี heading ใหม่ + D-id + แก้ parser (UX Critic U2) · เนื้อหาเก่าเร็วถ้าไม่มีคนอัปเดต (คำถามข้อ 7) · รอบแรกใช้ Bio ย่อหน้าสุดท้ายแทนได้ |
| การ์ด Interests **"มีไอคอนต่อหมวด"** + คำอธิบาย | **เก็บการ์ดไว้ใน Must แต่ย้ายไอคอนไป Nice** · คำอธิบายรายหมวด → Should | ไอคอนเป็นงานตกแต่ง ไม่ใช่ความสามารถหลัก · คำอธิบายต้องเปลี่ยนรูปแบบ Interests (U1) ซึ่งกระทบสัญญา `/api/interests` ระหว่าง FE ↔ BE — ไม่ควรเร่งในรอบแรก |
| **Guestbook** | **คงไว้ใน Must เฉพาะเมื่อ**ทำขั้นต่ำ 5 ข้อใน R3 ครบ · ถ้าไม่ครบ → **ย้ายไป Should** | ความเสี่ยง abuse + privacy (R3, R4) สูงที่สุดในทั้ง list · ฟีเจอร์ที่ลบข้อความไม่ได้ไม่ควรขึ้นเว็บจริง |
| Contact — **"แสดง email เป็น placeholder"** | **ตัดวลีนี้ทิ้ง** เปลี่ยนเป็น "ซ่อน email จนกว่าจะมีของจริง" | แสดงอีเมลปลอม = ทำร้าย credibility (R7) |
| Contact form ทั้งก้อน | **คงไว้** แต่ผูกเงื่อนไขกับคำถามข้อ 1 | ถ้าเจ้าของไม่มีทางอ่านข้อความ ฟอร์มก็คือคำสัญญาที่รักษาไม่ได้ (R1) |
| JSON-LD `Person` | **คงไว้** แต่เขียนขอบเขตให้ชัดว่า field ไหนห้ามใส่ | เล็กและทำง่าย แต่เป็นจุดที่ข้อมูลหลุดไปถึง agent ได้เงียบที่สุด |

## รอบ 2 — จำลองทีม (Teams) · 2026-09-25

> Facilitator: Claude (session หลัก) · Input: `docs/PROFILE.md` + สถานะหลัง Lab 04 (UI บน PR #7)
> **ไม่เปิดประเด็นที่ D1–D9 ปิดแล้วซ้ำ** — โฟกัสเรื่องที่ยังค้าง: OPEN_LOOPS L4, L8, ส่วน Now, ความน่าเชื่อถือของเนื้อหา, การ index, มือถือ · สถานะ: เปิดถกเถียง ข้อสรุปที่อนุมัติไปอยู่ `DECISIONS.md` (D10+)

### บทสนทนา (ย่อ)

**รอบที่ 1**

- **Brand Strategist:** เว็บตอนนี้ "น่ารัก สะอาด" แล้ว แต่เพื่อนที่เข้ามาครั้งที่สองจะเจอหน้าเดิมทุกอย่าง — ไม่มีเหตุผลให้กลับมา ส่วน Now คือสิ่งเดียวที่ทำให้เว็บ "มีชีวิต" ขอดึงกลับมาใน v1
- **UX Critic:** เห็นด้วยว่ากลุ่มเพื่อนต้องการ "ช่วงนี้ทำอะไร" แต่ปัญหาเร่งกว่าคือ **มือถือ** — nav 5 รายการภาษาไทยจะล้นจอ 360px และ headline ยาวขึ้นหลัง D1 ต้องตัดบรรทัดสวย ๆ · และฟอร์มติดต่อยังไม่บอกว่า "จะได้คำตอบทางไหน"
- **Devil's Advocate:** Now ที่อัปเดตครั้งเดียวแล้วค้าง 3 เดือน = ป้ายบอกว่าเว็บร้าง · และที่หนักกว่า: **L4 ยังไม่มีคำตอบ** — ข้อความ Contact ลง SQLite แล้วไม่มีใครเห็น ต่อให้ copy ไม่สัญญาเกินจริง ฟอร์มก็ยังเป็นหลุมดำ · อีกเรื่อง: `FALLBACK` ใน `profile.ts` ยังมี "Personal branding site" + อังกฤษ "coming soon" ถ้า PROFILE หายตอน deploy คนจะเห็นทันที

**รอบที่ 2**

- **Brand Strategist:** ยอมเรื่อง Now ถ้ามี **วันที่อัปเดตล่าสุด** แสดงคู่เสมอ — ความสดใหม่ที่ซื่อสัตย์ดีกว่าความสดใหม่ปลอม · ส่วน Contact: brand เสียจากการเงียบมากกว่าการไม่มีฟอร์ม ขอให้เจ้าของมีจังหวะอ่านที่ทำได้จริง แม้แค่สัปดาห์ละครั้ง
- **UX Critic:** เสนอ Now แบบ "ไม่แสดงถ้าเก่ากว่า 60 วัน" เพื่อไม่ต้องพึ่งวินัยคนอัปเดต — แต่ต้องมี heading ใหม่ + วันที่ใน PROFILE = แก้ parser · ถ้ายังไม่พร้อม ให้เลื่อนไปพร้อมกัน ไม่ครึ่ง ๆ กลาง ๆ · มือถือ: nav ต้องตัดบรรทัดได้หรือย่อ ไม่มี scroll แนวนอน
- **Devil's Advocate:** ถ้า Now ต้องแก้ parser ก็อย่าเร่งก่อน ship — ใส่ไว้หลังเว็บออนไลน์และเจ้าของลองอัปเดต PROFILE จริงสักรอบ · Contact: ทางออกเล็กสุดคือ BE ทำ script อ่าน/ลบข้อความ (เหมือน guestbook) + กำหนด retention เริ่มต้น แล้วให้เจ้าของยืนยัน — **ห้าม ship ถ้าเจ้าของยังไม่มีทางอ่านข้อความ** · robots: เว็บตั้งใจให้ agent อ่าน แต่ `/guestbook` กับ `/api/` ไม่ควรถูก crawl

### Brand Strategist (สรุปรอบ 2)

- ยอมเลื่อน Now แต่ขอเงื่อนไขว่าเมื่อทำต้องแสดงวันที่อัปเดตเสมอ
- ความเงียบหลังส่ง Contact ทำร้าย brand มากที่สุด → เจ้าของต้องมีจังหวะอ่านที่ทำได้จริง
- ไม่มีข้อเสนอเปลี่ยน headline/tagline เพิ่ม — D1 ใช้ได้ใน v1

### UX Critic (สรุปรอบ 2)

- มือถือ 360px: nav + headline ต้องไม่ล้น ไม่มี scroll แนวนอน
- Now: ถ้าทำ ให้ซ่อนอัตโนมัติเมื่อเก่าเกินกำหนด (ต้องแก้ parser → ไม่ใช่ v1)
- FALLBACK ต้องเป็นข้อความไทยกลาง ๆ ที่ผู้เยี่ยมอ่านแล้วไม่งง

### Devil's Advocate (สรุปรอบ 2)

- **Blocker ก่อน ship:** เจ้าของต้องมีวิธีอ่าน (และลบ) ข้อความ Contact + retention เริ่มต้น
- FALLBACK ที่มีข้อความอังกฤษ/ศัพท์คนทำเว็บ = leak รูปแบบหนึ่ง แก้ก่อน ship
- robots: ให้ index หน้าเนื้อหาได้ แต่กัน `/guestbook` และ `/api/`
- ค้าน scope creep: Now + parser ใหม่ไว้หลัง ship
